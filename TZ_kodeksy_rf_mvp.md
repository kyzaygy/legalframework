# Техническое задание: сайт «Кодексы и Конституция РФ» (MVP)

## 1. Цель и границы

Бесплатный сайт со всеми действующими кодексами РФ и Конституцией. Тексты в актуальной редакции, удобная навигация по структуре кодекса, поиск по статьям. Главный канал трафика — поисковые системы, поэтому приоритет: серверный рендеринг, корректные адреса, скорость, читаемость с телефона.

**В MVP входит:**
- Все действующие кодексы РФ + Конституция.
- Просмотр структуры кодекса (дерево: часть → раздел → глава → статья).
- Страница отдельной статьи с постоянным адресом.
- Поиск: по реквизиту (например, «ст 105 УК») и полнотекстовый по содержанию.
- Адаптивная вёрстка, читаемая с телефона.
- Карта сайта и базовое SEO.

**В MVP НЕ входит (не реализовывать):**
- Регистрация, личные кабинеты, комментарии.
- Образцы документов, инструкции, любой редакционный контент.
- Раздел юридической помощи, формы заявок, передача данных третьим лицам.
- Мобильное приложение.
- Перелинковка между статьями (ссылки вида «ч. 1 ст. 105» как кликабельные) — этап 2.
- История редакций и просмотр текста на произвольную дату — храним только действующую редакцию, но дату редакции фиксируем в данных.

Персональные данные на этом этапе не собираются, поэтому требования 152-ФЗ пока не активируются. Это появится на этапе юридической помощи.

## 2. Источник данных

Единственный источник — официальный портал правовой информации `pravo.gov.ru`.

Известно на момент составления ТЗ:
- С 1 июля 2022 года официальный статус имеют и консолидированные тексты актов с внесёнными изменениями, размещённые на портале.
- На портале есть раздел открытых данных в машиночитаемом формате на условиях свободного бесплатного использования.
- Кодексы: раздел `/codex/`. Конституция: раздел `/constitution/`. Актуальный перечень кодексов брать с портала, не зашивать вручную.

Точный формат отдачи структуры кодексов заранее не определён. Это выясняется на этапе разведки (см. раздел 5).

## 3. Технический стек

- **Фреймворк:** Next.js (App Router), TypeScript. Статически генерируемые страницы статей и кодексов (SSG/ISR) + серверный маршрут для поиска.
- **База данных:** PostgreSQL. Хранение текстов и полнотекстовый поиск в одной системе (встроенная конфигурация `russian`).
- **ORM:** Prisma.
- **Модуль загрузки данных:** отдельные скрипты на TypeScript (HTTP-клиент + парсер HTML/XML). Допустимо вынести парсинг на Python, если формат источника окажется XML-ориентированным; в остальном стек единый.
- **Инфраструктура:** один VPS в РФ, Docker Compose (приложение + PostgreSQL). Для MVP этого достаточно.

Стек — рекомендованный по умолчанию. Замены допустимы только с явным обоснованием, без усложнения инфраструктуры.

## 4. Модель данных

Три сущности. Структура кодекса — дерево произвольной глубины, потому что у разных кодексов разный набор уровней. Конституция хранится как обычный кодекс, без отдельной логики.

```prisma
model Code {
  id          String           @id @default(cuid())
  slug        String           @unique
  title       String
  shortName   String
  editionDate DateTime?
  sourceUrl   String?
  order       Int
  units       StructuralUnit[]
  articles    Article[]
}

model StructuralUnit {
  id       String           @id @default(cuid())
  code     Code             @relation(fields: [codeId], references: [id])
  codeId   String
  parent   StructuralUnit?  @relation("UnitTree", fields: [parentId], references: [id])
  parentId String?
  children StructuralUnit[] @relation("UnitTree")
  type     UnitType
  number   String?
  title    String
  order    Int
  articles Article[]
}

model Article {
  id          String          @id @default(cuid())
  code        Code            @relation(fields: [codeId], references: [id])
  codeId      String
  unit        StructuralUnit? @relation(fields: [unitId], references: [id])
  unitId      String?
  number      String
  slug        String
  title       String?
  bodyHtml    String
  bodyText    String
  status      ArticleStatus   @default(ACTIVE)
  editionDate DateTime?
  order       Int

  @@unique([codeId, slug])
}

enum UnitType {
  PART
  SECTION
  CHAPTER
  PARAGRAPH
}

enum ArticleStatus {
  ACTIVE
  REPEALED
  FUTURE
}
```

- `bodyHtml` — текст статьи с сохранённой структурой абзацев, нумерованных пунктов и таблиц; рендерится напрямую. При сохранении прогонять через белый список тегов (`p`, `ol`, `ul`, `li`, `table`, `tr`, `td`, `b`, `i`, `sup`).
- `bodyText` — тот же текст без разметки, для полнотекстового поиска.
- `number` — строкой, потому что встречаются составные номера: `105.1`, `12.1`.
- Полнотекстовый индекс (GIN, конфигурация `russian`) по `bodyText` и `title` добавляется отдельной SQL-миграцией.

## 5. Загрузка данных

Самый рискованный модуль. Выполняется первым и поэтапно.

**Этап 5.1 — разведка.** Взять один небольшой кодекс (например, Семейный). Определить, что использовать как источник: открытые данные портала или парсинг страницы консолидированного текста. Распарсить его в модель из раздела 4 целиком: дерево структуры + все статьи с корректными `bodyHtml`/`bodyText`. Цель — подтвердить, что модель данных сходится с реальными текстами. Если открытые данные непригодны, fallback — парсинг HTML-страницы консолидированного текста кодекса с портала.

**Этап 5.2 — массовая загрузка.** Повторяемый скрипт импорта, прогоняемый по всему перечню кодексов и Конституции. Скрипт идемпотентен: повторный запуск обновляет записи, а не плодит дубли. Допустимо, что первая загрузка требует ручного контроля по каждому кодексу — полная автоматизация обновления выносится в этап 2.

**Требования к импорту:**
- Сохранять `sourceUrl` и `editionDate` для каждого кодекса.
- Помечать статьи со статусом `REPEALED` отдельно, не удалять.
- Логировать расхождения структуры, чтобы их можно было проверить вручную.

## 6. Страницы и навигация

Четыре типа экранов:

1. **Главная.** Список всех кодексов и Конституции. Строка поиска на видном месте.
2. **Страница кодекса.** Оглавление в виде раскрываемого дерева структуры с переходами к статьям.
3. **Страница статьи** — основной экран сайта. Заголовок и номер статьи, текст, хлебные крошки (Кодекс → Глава → Статья), переходы на предыдущую и следующую статью внутри кодекса.
4. **Страница результатов поиска.** Список найденных статей с указанием кодекса и фрагментом совпадения.

## 7. Адреса и SEO

- Каждый кодекс — стабильный slug: `uk-rf`, `gk-rf`, `sk-rf`, `zhk-rf`, `zk-rf` и т.д. Конституция — `konstituciya`.
- Статья: `/{code-slug}/statya-{number}`, например `/uk-rf/statya-105`, `/uk-rf/statya-105.1`.
- Адреса постоянные и не меняются после публикации.
- Каждая страница статьи: уникальный `<title>` и meta-description, canonical-адрес.
- `sitemap.xml` со всеми статьями, `robots.txt`.
- Серверный рендеринг готового HTML (не клиентская подгрузка контента), чтобы страницы индексировались.
- Целевая скорость загрузки страницы статьи — быстрая на мобильном соединении; контент не должен зависеть от выполнения тяжёлого JS.

## 8. Поиск

Два режима в одной строке:

- **По реквизиту.** Нормализатор распознаёт шаблоны вида «ст 105 УК», «статья 14 СК», «ст. 105.1 УК РФ»: сопоставляет аббревиатуру кодекса и номер статьи и сразу ведёт на нужную статью. Карта аббревиатур кодексов задаётся явно.
- **Полнотекстовый.** Если реквизит не распознан — поиск по `bodyText` и `title` через полнотекстовый индекс PostgreSQL (`russian`), результаты ранжируются по релевантности.

Для MVP достаточно PostgreSQL FTS. Если качество русскоязычного поиска окажется недостаточным, на этапе 2 заменить на выделенный движок (Meilisearch / Manticore) — это не меняет модель данных.

## 9. Адаптив и читаемость

Функциональные требования (визуальное оформление приходит отдельным дизайн-брифом):
- Mobile-first, корректная вёрстка от узкого экрана телефона до десктопа.
- Основной упор — комфортное чтение длинного юридического текста с телефона: ограниченная ширина строки, достаточный межстрочный интервал и размер шрифта, читаемая вёрстка нумерованных пунктов.

## 10. Деплой

- Docker Compose: приложение Next.js + PostgreSQL.
- Хостинг — VPS в РФ.
- Переменные окружения вынесены в конфигурацию, не в код.
- Воспроизводимая сборка: проект поднимается из репозитория одной командой.

## 11. Порядок выполнения

1. Каркас проекта, схема БД, миграции, полнотекстовый индекс.
2. Этап 5.1 — разведка источника и загрузка одного кодекса, проверка модели.
3. Этап 5.2 — массовая загрузка всех кодексов и Конституции.
4. Страницы и навигация (раздел 6).
5. Адреса и SEO (раздел 7).
6. Поиск (раздел 8).
7. Адаптив и читаемость (раздел 9).
8. Деплой (раздел 10).

## 12. Критерии готовности

- Все действующие кодексы РФ и Конституция загружены с корректной структурой дерева.
- У каждой статьи свой постоянный адрес, страница открывается и отдаёт готовый HTML.
- Дерево кодекса разворачивается и ведёт к статьям; работают переходы между соседними статьями.
- Поиск по реквизиту ведёт прямо на статью; полнотекстовый поиск возвращает релевантные статьи.
- Сайт корректно и читаемо отображается на телефоне.
- Присутствуют `sitemap.xml` и `robots.txt`, у статей уникальные title и meta.
- Проект собирается и поднимается из репозитория одной командой.
